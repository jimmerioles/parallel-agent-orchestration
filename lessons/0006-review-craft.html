Lesson 0006 · ~20 minutes · hands-on drill

Review Craft

Trust calibration: spend your attention where the risk is — not evenly across the diff.

The one idea

Review is the bottleneck of everything you’ve built (Lesson 0001’s law) — and AI-authored diffs break the assumptions old review habits were built on. There is no author to interrogate, no hesitant naming, no “not sure about this” comment. Generated code arrives uniformly fluent and uniformly confident, whether it is right or wrong. A JetBrains Research study with Lund University puts it sharply: reviewing agent output “is not a diffing problem, but a trust-calibration problem” — knowing where to look hard and where you can afford to skim (JetBrains, Oct 2026).

The stakes are measurable. DORA’s 2025 report: 90% of developers use AI, but 30% report little or no trust in its output, and AI adoption correlates with higher delivery instability unless control systems — tests, version control, fast feedback, review — absorb the extra volume (DORA 2025). Simon Willison’s list of what LLMs reward starts with “a culture of code review”: if you’re fast and good at review, agentic work pays off (Vibe engineering, 2025).

Rubber-stamping is the failure mode: approving fast, running nothing, asking nothing. It feels like productivity and behaves like a silent lost update — at the level of whole changesets.

The five moves

MoveWhat you doFailure it kills
1 · Intent firstReread the brief, then git diff --stat. Does the file list match the brief — nothing extra, nothing missing? If it surprises you, stop and ask before reading code.Scope creep; a beautiful diff solving the wrong problem.
2 · Verify before inspectRun the acceptance command from the brief first. Red? Send it back — don’t spend review on a failing change.Reviewing the wrong revision; wasting attention.
3 · Overview → files → linesStart in hunk’s sidebar: how many files, how big, what kind? Stratify risk before reading a line.Line-by-line audits that scale terribly.
4 · Read risk-firstWhere does plausible-but-wrong hide? Deletions, changed tests, swallowed errors (2>/dev/null, bare catch), invented APIs, silent defaults, new dependencies.The confident lie — code that looks reviewed already.
5 · Run it, don’t just read itExecute the change against an edge case you chose. Ten minutes running beats thirty minutes reading (Analyst Engineering).Bugs that only appear at runtime.

Sources for the moves: JetBrains’ three-level workflow (overview before files, files before lines); GitHub’s “Review AI-generated code” (functional checks first, spot AI-specific pitfalls); Analyst Engineering (intent → tests → code, then run it).

The review seat: hunk

You’ve used hunk twice; this lesson adds its two review-craft features:

  • Rationale sidecars. An agent can ship a JSON file of notes and rationale next to its diff: hunk diff <base> <branch> --agent-context notes.json. Treat every note as a claim to verify, never as evidence.
  • Watch mode (hdw): review as the working tree changes — useful when you and an agent iterate on the same change.

The drill: a branch lands on your desk

A local branch review-drill exists in this repo. The brief that supposedly produced it:

The brief it was built from

“Add sandbox/tools/fleet-summary.sh: one line per git worktree, formatted <branch> <clean|dirty>, using the same dirty semantics as sandbox/tools/repo-state.sh. Do not modify any other file.”

It contains three planted defects. Find them before you reveal the answers.

  1. Review it cold. From your shell tab:

    hunk diff dsv41fmax review-drill

    Work the five moves in order. Write down each defect you find and which move caught it. Do not read ahead.

  2. Now add the agent’s rationale — the notes it shipped beside the diff:

    hunk diff dsv41fmax review-drill --agent-context reference/review-drill-rationale.json

    Compare its claims against what you found. Which claims are true, and which are confident and false? This is the whole lesson in one screen.

  3. Reveal and score yourself — only after you’ve written your three findings.
Reveal the three planted defects
  1. Scope creep: the diff also edits branches.sh — dropping | sort, silently breaking its “sorted” contract. Caught by move 1: git diff --stat shows a file the brief never mentioned. The rationale calls it “redundant” — a claim, not a reason.
  2. Wrong output: the script prints refs/heads/dsv41fmax, not dsv41fmax. Porcelain output gives full ref names, and the script never strips the prefix. Caught by move 5: run it. Also visible in move 4 if you read the parsing closely.
  3. Silent semantic gap: it uses git diff --quiet, which misses untracked and staged changes — so it says clean where repo-state.sh says dirty, breaking the brief’s “same dirty semantics” clause. Caught by move 4 (read risk-first) or by cross-checking against the reference tool from move 5. The rationale literally states the flaw as a feature (“untracked files are ignored so the check stays fast”).

Clean up the drill branch when done (it was never meant to merge):

git branch -D review-drill
You’ve won when

You found all three defects before revealing them, and you can name the move that catches each. Bonus: you spotted that every false rationale was more confident than the true one.

Check your understanding

What is the goal when reviewing AI-generated code?

Uniform confidence means equal-depth reading doesn’t scale. Allocate effort by risk: hard where it matters, skim where it doesn’t.

What should you do before reading a single line?

Verify before inspect: a failing change goes back, not through a line-by-line review. The acceptance command is your first filter.

Which is an AI-specific review red flag?

A test changed to go green without a requirement change removes evidence. Block on it, whoever or whatever wrote it.
