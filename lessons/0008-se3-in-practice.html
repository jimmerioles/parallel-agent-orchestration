Lesson 0008 · ~20 minutes · finale + capstone

SE 3.0 in Practice

The discipline you’ve been building — and what stays human.

Where you are

Eight lessons ago, two agents in two panes was the goal. You now run a fleet under a WIP limit, isolate with worktrees, brief with verification, review with trust calibration, and delegate the orchestration itself to an agent that behaves like you. The SASE framework calls the two halves of what you built the Agent Command Environment (your orchestration surface — herdr) and the Agent Execution Environment (where agents act — worktrees, test commands, permissions). You have lived both (Hassan et al., 2025).

The last skill is the one that makes all of it compound: harness engineering.

Harness engineering

The idea, from Mitchell Hashimoto: “anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again” (2026). Addy Osmani’s consolidation adds the practice: fix the environment — a rule, a permission, a tool, a skill — instead of correcting the output each time (2026).

You’ve been doing it implicitly all course: installing the herdr and hunk skills; baking the wait gotcha into the manager brief; creating the shell-review primer after your 2/3 drill; treating commit-as-accept as convention. The capstone makes it explicit — and permanent.

Capstone · Encode your conventions

Every agent that works in this repo reads AGENTS.md at the start. Anything you put there becomes the environment’s default behavior — the harness. Your task: adapt the template below to say what you want future agents to obey, add it to AGENTS.md, and commit.

  1. Draft your orchestration conventions. Start from these six — edit, cut, or add. One of them exists because of something you felt yesterday.

    ## Orchestration conventions (this repo) - One task · one branch · one worktree · one agent. Writes stay single-threaded; merge deliberately. - Every brief includes Goal, Deliverable, Constraints, Verification, Report. No verification command, no delegation. - Commit = accept. Agent output is committed only after the human runs the verification. - Parallelize only independent, precisely specified, machine-verifiable, low-stakes work. WIP limit: 3. - Control room is herdr: agent prompt without --wait; agent wait with the default until; parse IDs from JSON responses. - Rationale is a claim, not evidence. Agent notes and sidecars must be verified against the diff and the acceptance command.

    That last rule is yours to keep: in the debrief you said the agent’s notes made you understand the change faster and trust it more. The first is the feature. The second is exactly what this rule protects against — the trust has to stay earned.

  2. Add it to AGENTS.md (any editor), then commit it as the harness change it is:

    git add AGENTS.md hunk diff --staged git commit -m "docs: add orchestration conventions to AGENTS.md"
You’ve won when

AGENTS.md contains conventions you actually believe, committed — and you can name which future agent mistake each rule prevents. That is harness engineering: the lesson outlives the session because the environment now carries it.

What stays human

1 · INTENT
Deciding what is worth building and what “good” means. Agents optimize what you ask for; they can’t want the right thing for you.

2 · ACCEPTANCE
The merge click. Verification before trust — the acceptance command runs before the commit lands, every time.

3 · ACCOUNTABILITY
“The agent wrote it” doesn’t cut it (Osmani, “Own the Outer Loop,” 2026). Your name is on the diff.

4 · RESTRAINT
Knowing when not to parallelize. The counter-evidence is real: reported multi-agent gains often shrink when compute is matched (MAST, 2025). Coupled, fuzzy, high-stakes work stays single-threaded.

5 · TASTE
Design, naming, and the judgment no acceptance command covers. This is where seniority compounds.

The other parallelism: subagents

One path this course didn’t take: opencode’s built-in subagents — an agent spawning clean-context helpers in-process (a search agent, a reviewer, a general worker) via its task tool, defined as markdown files in ~/.config/opencode/agents/ (docs). Rule of thumb:

SubagentsHerdr workers
ShapeIn-process; returns a distilled summaryIndependent CLI session with its own terminal
Best forRead-heavy fan-out: search, explore, review — Cognition’s “intelligence” agentsWrites, long tasks, model mix, visible state, human triage
CostCheaper; context-isolatedFull session; your review bandwidth

Cognition’s 2026 rule covers both: extra agents contribute intelligence; writes stay single-threaded. Subagents are the cheapest way to add a reader.

Final check

What is harness engineering?

Turn every agent mistake into an environment fix — a rule, a permission, a tool, a skill — so the mistake can’t recur. Your AGENTS.md section is exactly this.

What stays human in the loop?

Mechanics moved to agents; judgment didn’t. You decide what to build, whether it lands, and you carry the name on the diff.

What is an agent rationale note?

The drill’s rationale argued for a bug. You felt the pull yesterday: notes speed understanding and raise trust — verify both against the diff and the command.
