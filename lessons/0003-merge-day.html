Lesson 0003 · ~15 minutes · hands-on

Merge Day

Isolation sent the bill. Pay it visibly — one conflict, resolved by hand.

The one idea

Worktrees didn’t make collisions impossible — they postponed and contained them. The integration step you deferred is now due: merging the worker branches back into your course branch. Here is the payoff. Where Lesson 0002’s collision was silent and destructive, a merge collision is loud and safe: git refuses to guess, stops, and asks you to decide (Pro Git, §3.2 Basic Branching and Merging).

This is why “merge conflict” shouldn’t scare you: a conflict is the system working. Nothing is lost; a human is simply required — which, in this discipline, is the point.

Plan: review and accept each worker’s branch, merge them one at a time, resolve the conflict by combining both contributions, then retire the worktrees.

Part 1 · Accept each worker’s branch

Your two worker checkouts each hold one new file, still uncommitted. In a real run this is where you’d read the diff. Do it for worker-a first: click its workspace in the sidebar, open a shell tab (ctrl+space then c), and run:

  1. Review and commit in worker-a:

    git status --short git add sandbox/shared/notes.md git diff --cached git commit -m "notes: accept worker a"

    status shows the new file; diff --cached shows exactly what you’re accepting (the whole file — it’s new); the commit records it on the worker-a branch.

  2. Same in the worker-b workspace — new shell tab, same commands with the other message:

    git status --short git add sandbox/shared/notes.md git diff --cached git commit -m "notes: accept worker b"

Part 2 · Merge, one at a time

Now go back to the teaching workspace and its shell tab. First, clear the Lesson 0002 artifact — the never-accepted file the losing worker left behind:

  1. Remove the collision artifact, then merge the first worker:

    rm -rf sandbox/shared git status --short git merge worker-a

    This one is easy: worker-a’s commit sits directly on top of your branch, so git just moves the pointer — a fast-forward.

    Sidenote worth knowing: if you skip the rm, git refuses the merge — “untracked working tree files would be overwritten.” That refusal is protection, not failure; clear the artifact and merge again.

  2. Merge the second worker — and meet the conflict:

    git merge worker-b git status --short

    CONFLICT (add/add): Merge conflict in sandbox/shared/notes.md. Both branches added the same file from the same base, with different content. Git stopped.

  3. Resolve it by hand. Open the file in your editor:

    $EDITOR sandbox/shared/notes.md

    You’ll see markers like this — yours, theirs, and the fence git inserted:

    <<<<<<< HEAD # Shared notes A: isolated in my own worktree. ======= # Shared notes B: isolated in my own worktree. >>>>>>> worker-b

    Make the file read exactly this — one heading, both lines, no marker lines:

    # Shared notes A: isolated in my own worktree. B: isolated in my own worktree.

    Then stage and conclude the merge:

    git add sandbox/shared/notes.md git commit -m "merge: combine worker notes"

    Chickened out? Before you commit, git merge --abort rewinds everything — conflicts are never a corner you can’t back out of.

  4. Verify the integration:

    cat sandbox/shared/notes.md git log --oneline --graph --all -8

    Both contributions, one file, one history. The graph shows the branch and the merge point.

Part 3 · Retire the worktrees

The branches are merged, so the checkouts have done their job. Find their herdr workspace IDs, then remove each checkout — herdr runs git worktree remove and closes the workspace, but keeps the branch:

  1. List the worker workspaces:

    herdr worktree list | jq -r '.result.worktrees[] | select(.branch | startswith("worker-")) | "\(.branch) \(.open_workspace_id)"'

    Two lines, e.g. worker-a w27 and worker-b w28. Note each ID.

  2. Remove each checkout (substitute your IDs):

    herdr worktree remove --workspace <worker-a-id> herdr worktree remove --workspace <worker-b-id>

    If git refuses because the checkout is dirty: look first. Add --force only when you truly mean “discard whatever is there.”

  3. Delete the spent branches and confirm:

    git branch -d worker-a worker-b git worktree list

    -d (not -D) only deletes branches that are fully merged — if git refuses, something didn’t make it in, and you want to know. You should be back to two checkouts: main and this course worktree.
You’ve won when

sandbox/shared/notes.md contains both A’s and B’s lines, the log shows a merge commit, and git worktree list is back to two checkouts with both worker branches deleted.

What just happened

You closed the loop that Lesson 0002 opened: isolation bought conflict-free parallel work, and integration paid for it with one small, visible, human decision. That trade — defer the collision, make it loud, resolve it on purpose — is the core economics of parallel orchestration at any scale.

The Rule, complete

One task · one branch · one worktree · one agent · one deliberate merge. Parallel work you can’t integrate isn’t progress — it’s inventory.

Check your understanding

Why is a merge conflict better than a lost update?

A conflict is loud, non-destructive, and human-gated. A lost update is silent and unrecoverable. Prefer the failure mode you can see.

After isolation, what is the deliberate integration step?

Each branch is reviewed and accepted, then merged in sequence — first worker clean, second worker with a conflict you resolve by hand.

What does herdr worktree remove do to the branch?

It deletes only the checkout. Branches outlive worktrees, so you delete a spent branch yourself with git branch -d once it is merged.
