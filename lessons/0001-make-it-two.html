Lesson 0001 · ~10 minutes · hands-on

Make It Two

From one agent to a fleet of two — the atom every larger setup repeats.

The one idea

Software engineering is shifting from AI-assisted coding to agentic software engineering: instead of autocompleting lines, you state intent and AI teammates execute whole tasks — and your job becomes commanding, specifying, and verifying (Hassan et al., “Towards AI-Native SE (SE 3.0),” 2024; Hassan et al., SASE framework, 2025). The academic name for the screen you’re about to build is an Agent Command Environment: “a command center where humans orchestrate, mentor, and oversee agent teams.”

Here’s the catch. Agents scale — your attention doesn’t. Every result still has to pass through one human:

The law of the lifestyle

“AI-generated code needs to be reviewed, which means the natural bottleneck on all of this is how fast I can review the results.”
— Simon Willison, “Embracing the parallel coding agent lifestyle,” Oct 2025

So parallelism only pays when the work is small, independent, and easy to check. That’s what today’s two-agent run is designed to prove — and next lesson, you’ll see exactly what happens when work is not independent.

Your control room: herdr

You’re already inside herdr — the persistent terminal workspace manager installed on this machine. Four words cover everything you need today:

  • Workspace — one per project. This conversation lives in one.
  • Tab — a layout of panes. You have one tab.
  • Pane — a real terminal, running an app (right now: opencode, your teacher).
  • Agent — a coding CLI herdr recognizes in a pane, with a live state.

The left sidebar is your command screen; herdr calls this “the main Herdr workflow”:

opencode reports its own state to herdr natively — no extra setup. Claude, codex, and gemini also work; we start with opencode to keep variables low.

From the herdr docs

“Start several agents, let them work in parallel, and use the sidebar to see which project needs a decision, which one is still running, and which one is ready to review.” (herdr.dev/docs/agents)

Agent states you’ll meet today: working (leave it alone) and idle (your turn to review). Later: blocked — the agent needs you. The sidebar is a review queue, not a progress bar.

The win: run two agents at once

Target layout — your teacher keeps the left pane; two workers take the right:

You + teacherpane 1 (this opencode)
Worker Anew opencode
Worker Bnew opencode

Do the steps in order. Click each number when you finish it (they remember).

  1. Switch to the herdr window — the terminal where this conversation lives.

  2. Split the pane to the right. Press ctrl+space, release, then press v. (Mouse alternative: right-click a pane → split right. Your config also binds alt+shift+enter.)

    Result: two side-by-side panes. A new one opens in the same folder, with a shell prompt.

  3. Start Worker A. In the new pane type c and press Enter. c is Omarchy’s alias for opencode --auto — auto-approves tool use. Fine for this sandbox; on real code, permissions exist for a reason.

    Wait for the opencode TUI to appear. The sidebar should now list a second agent.

  4. Paste Worker A’s brief into that agent and press Enter:

    Create the file sandbox/hello/a.md in this repo. Its content must be exactly: the heading "# Worker A", a blank line, then one sentence in your own words describing what AI coding agent you are and which model you run on. Create or modify no other file. When done, reply with the single word: done

    Watch its sidebar state flip to working. Now walk away from it — that’s the whole point.

  5. Split again and start Worker B. Right-click the right-hand pane (or press ctrl+space then h) to split it downward. In the new pane run c, then paste Worker B’s brief:

    Create the file sandbox/hello/b.md in this repo. Its content must be exactly: the heading "# Worker B", a blank line, then one sentence in your own words describing what AI coding agent you are and which model you run on. Create or modify no other file. When done, reply with the single word: done

    Two agents, working at the same time, in the same checkout — and you haven’t written a line.

  6. Wait for both to go idle. Glance at the sidebar only. Do not sit and watch either agent — if you catch yourself spectating, that’s a habit to break.

  7. Review both results. In any pane, run:

    ls sandbox/hello/ && git status --short

    Open both files (your editor is one keystroke away: super+return). Check each against its brief: right heading, one sentence, nothing else touched. This is the review step — the reason the whole exercise exists.

    Heads-up: git status will also list this course’s own files as new — expected. What matters is that sandbox/hello/ contains exactly two files, each matching its brief.
You’ve won when

sandbox/hello/a.md and sandbox/hello/b.md both exist, each matching its brief, and you watched both agents’ states change in the sidebar without babysitting either terminal.

What just happened

You ran the atom of every orchestration setup — bigger fleets are just this loop with more workers and better plumbing:

brief→ delegate→ agents run in parallel→ review & accept

Two things made today safe. The tasks were independent (different files — no collisions) and trivially verifiable (you know exactly what correct looks like). That gives us the heuristic this course builds on:

The Rule

Hand work to a parallel agent only when it is independent, precisely specified, machine-verifiable, and low-stakes. Otherwise, fix one of those four first — next lesson does exactly that for independence.

Check your understanding

Retrieval beats rereading. Answer from memory:

What is the binding constraint on how much parallel agent work can land?

Agents scale almost free; every result still passes through one human’s review. Parallelism is only worth it when each result is cheap to check (Willison).

In herdr, what does the sidebar’s agent state tell you?

working = leave it; idle/done = ready to review; blocked = it needs you. It’s a review queue, not a progress bar (herdr docs).

When should you hand a task to a parallel agent?

Coupled, fuzzy, or hard-to-check work multiplies your review burden instead of your output. Fix independence and verification first; then parallelize.
