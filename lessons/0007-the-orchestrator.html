Lesson 0007 · ~25 minutes · hands-on

The Orchestrator

Delegate the orchestration itself — one agent that provisions, staffs, waits, and reports.

The one idea

For six lessons you have been the orchestrator. The SASE framework names your surface the Agent Command Environment: “a command center where humans orchestrate, mentor, and oversee agent teams” (Hassan et al., 2025). Herdr is a working instance of one. Today the mechanics move to an agent.

Cognition’s 2026 field report gives the pattern a shape: a manager splits work, children execute, the manager synthesizes — and writes stay single-threaded (“Multi-Agents: What’s Actually Working,” Apr 2026). So the orchestrator agent will create the worktree, start the worker, submit the brief, wait, and read the result. It will not write code and will not merge. Those stay with the worker and with you.

The boundary

The orchestrator owns mechanics; you keep judgment. The worker owns the write. One writer per artifact, always.

Part 1 · Upgrade the harness

Agents learn tools through skills. Install two — the herdr skill (so an agent can drive this machine’s control room) and hunk’s review skill (so an agent can steer a live review). Both are one-liners, and both stay in sync with upgrades:

  1. Install the skills in a shell tab:

    mkdir -p ~/.agents/skills/herdr ~/.agents/skills/hunk-review herdr --skill > ~/.agents/skills/herdr/SKILL.md ln -sf "$(hunk skill path)" ~/.agents/skills/hunk-review/SKILL.md ls ~/.agents/skills/herdr ~/.agents/skills/hunk-review

    The symlink is hunk’s own recommended method (“load or symlink that file … to keep it in sync across Hunk upgrades”). Skills load at session start — which is why the next step starts a fresh agent.

  2. Start a fresh orchestrator. Split a pane (ctrl+space then v) and run c in the new pane. Don’t reuse the old worker panes — their sessions started before the skills existed.

Part 2 · The manager brief

Paste this whole message into the orchestrator. It contains its own instructions plus the inner brief it must forward to the worker — a brief within a brief.

Use the herdr skill. You are the orchestrator. Provision one isolated worker, delegate the inner brief, wait for it, then report. Steps: 1. Create the worktree: herdr worktree create --cwd /home/jimmerioles/Work/parallel-agent-orchestration --branch orch-a --base dsv41fmax Parse .result.workspace.workspace_id and .result.root_pane.pane_id from the JSON response. 2. Start the worker in that pane: herdr agent start orch-worker --kind opencode --pane <pane_id> --timeout 60000 3. Submit the inner brief (no --wait): herdr agent prompt orch-worker "Create an executable script at sandbox/tools/worktree-count.sh (shebang #!/usr/bin/env bash, mode 755) that prints the number of git worktrees as a single integer, using git worktree list --porcelain. Create or modify no other file. Verify by running it. Then git add sandbox/tools/worktree-count.sh and git commit -m 'feat: add worktree-count tool'. Reply with just: done" 4. Wait for it: herdr agent wait orch-worker --timeout 300000 If this times out, inspect with herdr agent list and herdr agent read orch-worker --lines 30 before retrying; do not re-prompt blindly. 5. Read the report: herdr agent read orch-worker --lines 30 6. Report back to me: the branch name, the worker's final status, and the last 10 lines of its output. Constraints: use only the herdr CLI and git. Do not create or modify files yourself. Do not merge. Do not remove the worktree. Do not touch other workspaces or agents.

Part 3 · Watch the machine run

  1. Read the sidebar, not the terminals. The sequence you should see: orchestrator working → a new orch-a workspace appears → a new agent orch-worker starts and goes working → worker done → orchestrator reads and reports.

  2. If the orchestrator’s wait times out even though the worker finished: that’s a real herdr subtlety, not a bug in your machine. opencode can settle as done, and --until idle would miss it — which is why the brief says to use the default. Watch how the agent recovers; that recovery is part of the lesson.

  3. Confirm the write happened once: the worker committed in its own worktree — the orchestrator wrote nothing and merged nothing. That’s the single-writer rule holding at machine speed.

Part 4 · Review it live with an agent

Now the feature you asked about. Open the worker’s branch in hunk and leave it running:

  1. hunk diff dsv41fmax orch-a

  2. Ask your teacher to drive it. In this pane, paste:

    Load the Hunk skill and walk me through this live review.

    Watch the window move by itself: files and hunks navigated, inline comments anchored to lines. The agent contributes intelligence; the diff stays yours to judge. Leave a human note from the viewer if you want to feel the other side of the conversation.

Part 5 · Accept and clean up

The human keeps the accept step. Review done? Merge, retire the worktree, delete the branch:

git merge orch-a herdr worktree list | jq -r '.result.worktrees[] | select(.branch=="orch-a") | .open_workspace_id' herdr worktree remove --workspace <orch-a-id> git branch -d orch-a
You’ve won when

sandbox/tools/worktree-count.sh is merged into dsv41fmax, the orchestrator reported the worker’s status and output without you touching a worktree or agent command, and you watched an agent steer a live hunk review of the result.

What just happened

You moved up a level. The loop is the same one from Lesson 0001 — brief, delegate, verify, accept — but the orchestration mechanics now run inside an agent while your attention stays on judgment. That’s the Agent Command Environment in practice, and it’s how the pattern scales: your WIP limit now applies to orchestrators as much as workers.

Check your understanding

What does the orchestrator agent own?

It provisions, staffs, waits, and reports. You decide what’s worth doing and whether the result lands. The worker owns the write.

Why does the worker commit its own work?

Cognition’s 2026 rule: extra agents contribute intelligence, not actions. One writer per artifact; you merge deliberately after review.

Which wait command settles correctly?

The default matches idle, done, and blocked. Narrowing to --until idle misses opencode’s done state — the probe that built this lesson hit exactly that.
