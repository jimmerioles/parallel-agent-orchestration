Lesson 0002 · ~15 minutes · hands-on

Two Agents, One File

Watch work vanish silently — then make it impossible with git worktrees.

The one idea

Lesson 0001 was safe because each worker owned a different file. Real tasks rarely cooperate: two changes often touch the same module, the same config, the same file. Run two agents against one shared checkout and you get the classic failure of concurrent writes — the lost update. Nothing crashes. Nothing warns you. One agent’s work is simply gone, because both agents were told to bring the file to their version (Cognition: “actions carry implicit decisions”).

You cannot fix this with better prompting. You fix it with isolation: a git worktree gives each agent its own checkout of the same repository — its own files, its own branch, its own git state — so parallel work cannot trample itself. It is the same trick Anthropic documents for running parallel Claude Code sessions (Claude Code best practices), and herdr wraps it in one command (herdr CLI reference).

You already live in one

This lesson’s workspace is a git worktree (dsv41fmax) of parallel-agent-orchestration. Today you’ll make two more — one per worker.

Part 1 · Provoke the collision

You should still have Worker A and Worker B panes from Lesson 0001, both idle. If you closed them: split twice and run c in each. Both panes are in this same checkout — that’s the point.

  1. Give Worker A this brief (paste, Enter, wait for idle):

    Create or overwrite the file sandbox/shared/notes.md with exactly this content: the heading "# Shared notes", a blank line, then the line "A: two agents, one checkout." Create or modify no other file. Reply with just: done

  2. Give Worker B this brief (same file, same shape — wait for idle):

    Create or overwrite the file sandbox/shared/notes.md with exactly this content: the heading "# Shared notes", a blank line, then the line "B: two agents, one checkout." Create or modify no other file. Reply with just: done

  3. Inspect the damage. Open a shell — new tab: ctrl+space then c — and run:

    cat sandbox/shared/notes.md

    Only B’s line is there. A’s work is gone, and nothing reported a problem: not the agent, not git, not the sidebar. Sequential briefs can’t save you — and sent simultaneously it’s worse, a genuine race whose winner changes run to run.

One checkout

Both agents write the same file.

Last writer wins → lost update.

Shared git state → stashes, branch switches, index conflicts.

Two worktrees

Each agent owns a checkout.

Both versions survive → merge deliberately.

Independent git state → no interference.

Part 2 · Manufacture independence

A worktree is one repository with multiple working directories. Each gets its own branch, so each agent can edit “the same file” without ever touching the other’s copy. Herdr only starts worktree actions from the repo’s parent workspace — and you’re inside a linked worktree — so point --cwd at the main checkout when you create them:

  1. Create two worktrees, one per worker. Run each command in your shell tab, one after the other:

    herdr worktree create --cwd /home/jimmerioles/Work/parallel-agent-orchestration --branch worker-a --base dsv41fmax herdr worktree create --cwd /home/jimmerioles/Work/parallel-agent-orchestration --branch worker-b --base dsv41fmax

    Each command creates a checkout at ~/.herdr/worktrees/parallel-agent-orchestration/<branch>, branched from your course branch, and opens it as a new workspace — no focus stealing. Two new workspaces appear in the sidebar, grouped with this repo.

    Alternative to --cwd: switch to the parent workspace in the sidebar (the main checkout), open a shell tab there, and run the same commands without --cwd — but keep --base dsv41fmax, or you’ll branch from master instead.

  2. Send each worker into its own checkout. Click the worker-a workspace in the sidebar (or alt+↓ to cycle workspaces). In its pane, run c, then paste Worker A’s new brief:

    Create or overwrite the file sandbox/shared/notes.md with exactly this content: the heading "# Shared notes", a blank line, then the line "A: isolated in my own worktree." Create or modify no other file. Reply with just: done

  3. Do the same in the worker-b workspace — start c, then paste Worker B’s new brief:

    Create or overwrite the file sandbox/shared/notes.md with exactly this content: the heading "# Shared notes", a blank line, then the line "B: isolated in my own worktree." Create or modify no other file. Reply with just: done

  4. Verify both survived. Back in your shell tab, run:

    cat ~/.herdr/worktrees/parallel-agent-orchestration/worker-a/sandbox/shared/notes.md cat ~/.herdr/worktrees/parallel-agent-orchestration/worker-b/sandbox/shared/notes.md git worktree list

    One file, two agents, both versions intact — in separate checkouts on separate branches. git worktree list shows four checkouts: the main clone, this course worktree, and the two worker islands.
You’ve won when

Both worker-a and worker-b checkouts contain a sandbox/shared/notes.md with their own line, and git worktree list shows all four checkouts. Nothing was lost this time.

Leave them standing

Both worktrees stay for Lesson 0003, where you merge the branches and clean up. Merging is the tax isolation buys you — paid deliberately, in one place, instead of silently, in your file.

What just happened

The Rule from Lesson 0001 hasn’t changed — it says independent. Worktrees are how you make coupled work independent: same repository, separate worlds, one branch per worker. The failure mode moves from “silent lost update” to “visible merge,” and visible problems are the only kind you can manage.

The Rule, sharpened

Parallel agents may share history (one repository) but never a working directory. One task, one branch, one worktree, one agent — then merge on purpose.

Check your understanding

From memory:

Why did Worker A’s line vanish in Part 1?

Same directory, same file, two overwrites: last writer wins. No error surfaces anywhere — that’s what makes shared-checkout parallelism dangerous.

What does a git worktree give each agent?

A separate checkout with its own branch and git state, all sharing one repository history. Agents stop trampling each other; merging becomes an explicit step.

Parallel safety on a shared file comes from…?

Prompting cannot serialize concurrent writes. Isolate the writers, then merge their branches on purpose — the merge is made visible, not eliminated.
