Lesson 0005 · ~20 minutes · hands-on

The Fleet

Three agents, one work-in-progress limit, and a blocked worker to rescue.

The one idea

You now have every part: briefs (Lesson 0004), isolation (0002), integration (0003). A fleet is just those parts repeated — with one new discipline. The number of agents you run is not set by your machine; it is set by your review bandwidth (Lesson 0001’s law). Launch more than you can review and you are not managing a fleet, you are accumulating inventory. So you set a WIP limit — work-in-progress limit — and today it is three.

Gergely Orosz’s field reporting on parallel agents is blunt about the ceiling: senior engineers benefit, but review fatigue is the real cap — most people top out around a handful, not a swarm (Pragmatic Engineer, 2025).

The second new skill is triage. Agents don’t just run and finish — they can go blocked, waiting on you. Blocked agents cannot progress, so they jump the queue: blocked first, then review what’s idle, leave the working ones alone. You’ll engineer a blocked agent on purpose to practise the rescue.

Part 1 · Provision three worktrees

One task, one branch, one worktree, one agent. From your shell tab in this workspace (the `--cwd` workaround again, since herdr starts worktrees from the parent workspace):

  1. Create the fleet’s checkouts:

    herdr worktree create --cwd /home/jimmerioles/Work/parallel-agent-orchestration --branch fleet-a --base dsv41fmax herdr worktree create --cwd /home/jimmerioles/Work/parallel-agent-orchestration --branch fleet-b --base dsv41fmax herdr worktree create --cwd /home/jimmerioles/Work/parallel-agent-orchestration --branch fleet-c --base dsv41fmax

    Three new workspaces appear in the sidebar, grouped with this repo. Three independent worlds, three branches, no shared working directory.

Part 2 · Staff and brief the fleet

For each worker: click its workspace in the sidebar, start the agent in the pane, paste the brief. Note the deliberate difference for C — no c alias, plain opencode.

  1. Worker A — in the fleet-a workspace, run c (opencode auto), paste:

    Create an executable script at sandbox/tools/worktrees.sh (shebang #!/usr/bin/env bash, mode 755). It takes no arguments and prints one line per git worktree: the branch name, a single space, then the worktree path. Use git worktree list --porcelain. Create or modify no other file. Verify: ./sandbox/tools/worktrees.sh prints one line per worktree, including one for dsv41fmax and one for master, exit 0. Reply with just: done

  2. Worker B — in fleet-b, run c, paste:

    Create an executable script at sandbox/tools/branches.sh (shebang #!/usr/bin/env bash, mode 755). It takes no arguments and prints the local branch names, one per line, sorted alphabetically. Create or modify no other file. Verify: ./sandbox/tools/branches.sh prints dsv41fmax and master and the fleet branches, sorted, exit 0. Reply with just: done

  3. Worker C — in fleet-c, run plain opencode (no --auto), paste:

    Create an executable script at sandbox/tools/agents.sh (shebang #!/usr/bin/env bash, mode 755) that prints the names of the coding-agent CLIs available on PATH, one per line, sorted. Check exactly these names with command -v: opencode, claude, codex, gemini, crush, copilot, cursor-agent. Also create ~/.cache/parallel-fleet/ and write a copy of the script's output to ~/.cache/parallel-fleet/agents.txt. Do not modify any other file in this repository. Verify: ./sandbox/tools/agents.sh includes opencode and claude; diff <(./sandbox/tools/agents.sh) ~/.cache/parallel-fleet/agents.txt prints nothing; exit 0. Reply with just: done

    Worker C’s task writes outside its worktree, which opencode guards by default. Without --auto, it will stop and ask you — that is your blocked drill, engineered on purpose.

Part 3 · Run the fleet, then triage

  1. Step back. All three briefs are issued; the sidebar should show three agents working. This is the moment the fleet pays: you are free, not watching. Do not spectate.

  2. Rescue the blocked worker. Worker C will flip to blocked (you may also get a desktop notification). Click its workspace, read the approval prompt, and approve once — not “always”. Watch it flip back to working, then idle.

    Triage order, now practised: blocked first (it cannot move without you), then idle/done (ready to review), and working last (leave it alone). Approving “once” keeps the guardrail intact — the harness lesson for a later day.

Part 4 · Verify, accept, integrate

For each worktree: open a shell tab, run its verification, review with hunk, commit. The three files are independent, so this is Lesson 0003’s loop run three times.

  1. Verify and accept each worker (in its own workspace shell tab):

    # in fleet-a ./sandbox/tools/worktrees.sh git add sandbox/tools/worktrees.sh && hunk diff --staged && git commit -m "feat: add worktrees tool" # in fleet-b ./sandbox/tools/branches.sh git add sandbox/tools/branches.sh && hunk diff --staged && git commit -m "feat: add branches tool" # in fleet-c ./sandbox/tools/agents.sh && diff <(./sandbox/tools/agents.sh) ~/.cache/parallel-fleet/agents.txt git add sandbox/tools/agents.sh && hunk diff --staged && git commit -m "feat: add agents tool"

    Each verification is the one from that worker’s brief — you are checking the contract, not the vibes.

  2. Merge the fleet — back in this workspace’s shell tab:

    for b in fleet-a fleet-b fleet-c; do git merge "$b" -m "merge: $b"; done git log --oneline --graph -8

    Independent files mean clean merges (some fast-forward, some merge commits, depending on order). No conflict — because you chose independent work and isolated it. That was the whole point of Lessons 0002–0004.

  3. Retire the fleet. Find the workspace IDs, remove each checkout, delete the spent branches:

    herdr worktree list | jq -r '.result.worktrees[] | select(.branch | startswith("fleet-")) | "\(.branch) \(.open_workspace_id)"' # then, for each ID printed: herdr worktree remove --workspace <fleet-a-id> herdr worktree remove --workspace <fleet-b-id> herdr worktree remove --workspace <fleet-c-id> git branch -d fleet-a fleet-b fleet-c git worktree list
You’ve won when

Three tools landed on dsv41fmax (worktrees.sh, branches.sh, agents.sh), you rescued exactly one blocked agent without disabling its guardrail, and git worktree list is back to two checkouts with all three fleet branches deleted.

What just happened

You ran a fleet under a WIP limit, provisioned it with worktrees, delegated with briefs, triaged a blocked worker, and integrated three independent branches cleanly. That is the full basic loop at scale — the same loop, three times, with a queue discipline on top.

The Rule, at fleet scale

One task · one branch · one worktree · one agent · one deliberate merge — multiplied by a WIP limit you set from your review bandwidth, never from your core count.

Check your understanding

Why cap the fleet at three agents?

The cap comes from review bandwidth, not compute. Agents scale; your attention doesn’t. More agents than you can review is inventory, not throughput.

Which agent do you handle first?

A blocked agent cannot progress without you, so it is burning idle time. Working agents can wait; blocked ones can’t.

What must every fleet task have?

Independent so it can run in its own worktree, briefed so it can’t misread the goal, verifiable so “done” is provable. Coupled work multiplies review, not output.
