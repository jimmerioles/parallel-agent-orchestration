Lesson 0004 · ~15 minutes · hands-on

The Brief

Write the spec; the review becomes cheap. Delegation is a writing skill.

The one idea

Every lesson so far, the briefs were handed to you. From here on, you write them — because the brief is where the cost of review is decided. Simon Willison’s rule of thumb: code that “started from your own specification is a lot less effort to review,” while code that lands out of nowhere forces you to reverse-engineer its goals before you can judge it (Willison, 2025). Anthropic says the same thing from the other side: scope the task tightly and give the agent a way to verify its own work (Claude Code best practices).

This is the two hardest legs of The Rule — precisely specified and machine-verifiable — turned into a document you write before any agent starts. A brief is not a wish. It is a contract with a test.

Anatomy of a brief

PartAnswersExample fragment
GoalWhat and why, in one sentence“Give the manager a one-glance checkout state.”
DeliverableExact paths, exact format“Create sandbox/tools/repo-state.sh; two lines of output.”
ConstraintsWhat not to touch; tools allowed“Only git and coreutils; no other file changed.”
VerificationThe command that proves done“bash sandbox/tools/repo-state.sh prints the branch, then clean.”
ReportWhat to say back“Reply with the command output, nothing else.”

Keep it short. A good brief is usually five to eight lines. Length is not rigour — an explicit acceptance test is.

Bad brief, good brief

Same task, two briefs. The difference is not politeness — it is whether “done” can be checked by a machine or only argued about by a human.

Vague — unverifiable

“Improve the repo tooling. Make the scripts cleaner and more useful, and tidy up the docs. Use your best judgement.”

No deliverable. No boundary. No test. You will review by vibes and pay full price.

Precise — verifiable

“Create sandbox/tools/repo-state.sh. It prints the current branch on line one and clean or dirty on line two, using only git and coreutils. Change no other file. Verify: bash sandbox/tools/repo-state.sh prints dsv41fmax then clean; after touch sandbox/scratch it prints dirty. Reply with that output.”

One deliverable. One boundary. One test you can run in five seconds.

Red flags

  • Vague verbs: “improve”, “clean up”, “make nicer”, “refactor” — with no acceptance test attached.
  • No verification: if you can’t name the command that fails before and passes after, you are about to review vibes.
  • Open scope: “and anything else you notice.” Every extra noun is review debt you just bought.
  • Multiple deliverables: one brief, one branch, one reviewable change.
  • Missing boundaries: no list of files that must stay untouched.

Your turn: write a real brief

Here is the goal — you write the rest. Then you’ll run it past your teacher before spending an agent on it. That critique step is the feedback loop for this lesson.

Goal (given)

Make this sandbox a little more fleet-friendly: a script a manager can run inside any checkout to see, at a glance, what state it is in. Target path: sandbox/tools/repo-state.sh. You decide the exact output format, behaviour, constraints, and — most importantly — the verification commands.

  1. Draft your brief. Fill every field; don’t send it yet. Use this skeleton (or your own):

    Goal: <one sentence: what and why> Deliverable: sandbox/tools/repo-state.sh — <exact behaviour and output format> Constraints: <files not to touch; tools allowed; nothing else changed> Verification: <exact command(s) and expected output — the definition of done> Report: <what the worker should reply>

    Test yourself before the teacher does: run your verification commands mentally. Do they actually prove the deliverable? Would they pass on a broken script?

  2. Get it critiqued. Paste your draft into the teacher pane and ask: “Critique this brief against the five parts and the verification test.”

    Expect feedback like “your test passes even when the script is empty” or “this field is a goal, not a deliverable.” Revise until the teacher says it is runnable as-is.

  3. Send it to a worker. Reuse a worker pane from Lesson 0001 (both are still open in this workspace). Paste the revised brief, press Enter, wait for idle.

  4. Run your own verification — as written. In your shell tab, run the exact commands from your brief’s Verification section. Then the “before” state too, if your test needs it.

    A failed verification is not a failed lesson — it is information. Send the failure back to the same worker (“your output was X, expected Y”) and let it iterate. That loop is the job.

  5. Accept it. Review the diff with hunk, then commit:

    git add sandbox/tools/repo-state.sh hunk diff --staged git commit -m "feat: add repo-state tool"

    You specified it, an agent built it, a command proved it. That is the whole loop — now with your brief at the front.
You’ve won when

Your verification commands pass against the committed sandbox/tools/repo-state.sh, and the brief you sent would let a stranger reproduce that result without asking you a single question.

Check your understanding

What makes “done” provable in a brief?

If you can’t name a command that fails before and passes after, you’re about to review vibes. The test is the definition of done.

Which of these is a red flag in a brief?

Vague verbs with no acceptance test are unreviewable. The other three are exactly what a good brief contains.

What belongs in the Constraints section?

Constraints are boundaries: what stays untouched, which tools are allowed, and what “nothing else changed” means for this task.
