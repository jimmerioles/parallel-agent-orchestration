Subagents

The in-process fleet: a clean-context reviewer you @-mention.

The one idea

Everything so far ran agents as separate terminals. opencode has a second kind of parallelism built in: subagents — helpers a primary agent can spawn, each with its own clean context, its own permissions, and its own model, returning only a distilled summary (opencode docs).

You already have three built-in subagents: general (multi-step work), explore (fast, read-only codebase search), and scout (external docs and dependency research). And you can add your own — which is the clean-context reviewer Cognition describes: “a reviewer reads a diff and flags the bugs the coder can’t see” (2026). It’s the cheapest way to add intelligence, because no terminal, worktree, or merge is involved.

Where agents live

ScopePathUse for
Global~/.config/opencode/agents/Agents you want everywhere
Project.opencode/agents/ (in the repo)Agents this project’s harness needs — committed, inherited by future agents

The markdown filename becomes the agent name, so reviewer.md is invoked as @reviewer. Frontmatter carries description, mode: subagent, permission, model, and temperature.

We’ll create a project-scoped reviewer: it becomes part of this repo’s environment (Lesson 0008’s capstone in action), and it can only ever read.

Part 1 · Create the reviewer

  1. Write the agent file. In your shell tab, create .opencode/agents/reviewer.md with exactly this:

    --- description: Clean-context code reviewer. Read-only. Reviews diffs and changesets for defects, risk, and missing verification. mode: subagent temperature: 0.1 permission: edit: deny task: deny webfetch: deny websearch: deny bash: "*": deny "git *": allow "rg *": allow "grep *": allow "ls *": allow "cat *": allow "sed *": allow "head *": allow "tail *": allow "wc *": allow "find *": allow "test *": allow "./sandbox/tools/*": allow --- You are a meticulous code reviewer with a clean context: you did not write this code. Review the requested changeset or files. For every finding report: - file:line - what is wrong - why it matters (consequence, not opinion) - how to verify it (the exact command) Order findings by severity (blocker, major, minor). Run the code where permissions allow it — reading is not enough. If the change is clean, say so plainly and name the single riskiest thing you saw. End with a verdict: ACCEPT or REQUEST CHANGES. Do not modify any file.

    Tooling note: the intended path is opencode agent create, but on this machine it currently fails — Request is missing x-opencode-session (a routing bug in the opencode-go provider when it generates the prompt outside a session). Writing the file produces the same result; report the bug in the community step.

  2. Start a fresh opencode session — agents load at session start. Split a pane (ctrl+space then v) and run c. The old panes won’t see the new agent.

Part 2 · Point it at real work

  1. @-mention it with a genuine review task — your own toolkit:

    @reviewer Review the toolkit in sandbox/tools/ (repo-state.sh, worktrees.sh, branches.sh, agents.sh, worktree-count.sh). Run each one, check its parsing and error handling against the shell-review primer's rules, and report findings by severity with file:line and a verdict.

    Subagents are read-only here: edit: deny blocks every write, and bash is denied except the read-only commands plus running your tools. It physically cannot touch the repo.

  2. Watch the child session. The subagent runs as a child of the current session, in-process — it does not appear in herdr’s sidebar, because it isn’t a separate terminal. Enter it with the session_child_first binding (Leader + Down by default), cycle children with Right/Left, return with Up. It hands back a distilled summary, not a transcript.

  3. Weigh its findings against your own. You reviewed the toolkit family before; did the clean-context reviewer catch anything you missed — or claim anything false? Same rule as always: its notes are claims.

  4. Commit the agent — it’s harness now:

    git add .opencode/agents/reviewer.md hunk diff --staged git commit -m "chore: add project reviewer subagent"
You’ve won when

@reviewer produced a severity-ordered review of your toolkit with a verdict, you watched it run as a child session, and .opencode/agents/reviewer.md is committed — so every future agent in this repo inherits a read-only reviewer.

Subagent or herdr worker?

SubagentHerdr worker
RunsIn-process, as a child sessionOwn terminal pane, own workspace
ContextFresh, isolated; returns a summaryFull session you can read and steer
StateNot in the sidebarVisible state: working/blocked/done
Best forRead-heavy fan-out: search, explore, reviewWrites, long tasks, model mix, triage

Both obey the same law: extra agents contribute intelligence; writes stay single-threaded. Reach for a subagent when the work is reading; reach for a worktree worker when something must be written and merged.

Check your understanding

How do you invoke a subagent manually?

Type @reviewer (or let the primary agent invoke it via the task tool). Subagents can also be invoked automatically based on their description.

What does mode subagent mean?

Primary agents (build, plan) call subagents for focused work; you can also @-mention one directly. mode: all would make it usable both ways.

What does edit deny do for the reviewer?

It gates write/edit/patch — the reviewer can read and run allowed commands but physically cannot change your repo. Least privilege, enforced by the harness.
